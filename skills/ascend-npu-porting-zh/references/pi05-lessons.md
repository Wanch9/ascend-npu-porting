# π0.5：四卡适配与训练加速案例

本案例来自 [Wanch9/pi05-npu](https://github.com/Wanch9/pi05-npu)，实测日期 2026-10-11。
完整改动与命令见项目 README 和 NPU_PORTING.md；计时及梯度证据见项目 npu/optimization_summary.json。
这些是特定模型和运行时的历史结果，不是新任务的默认卡数、容差或兼容性承诺。

后续接入：项目常规 `scripts/train_pytorch.py` 已支持 `--pytorch-npu-training-optimization`，模型原生开关为 `gradient_checkpointing_enable(checkpoint_whole_stack=False)`；在 NPU/HCCL 初始化前配置确定性通信。下文“仅实验进程启用”描述原测量阶段，当前可通过常规入口显式开启，默认仍关闭。完整数据链路及新入口保存恢复的验收状态以项目报告为准。

## 实测契约与完成边界

- OpenPI `215abfb217dbac7d5f1273282331b9b1866c0479`，完整 π0.5 base，3,616,757,520 参数全部可训练。
- 单节点 4 × 910B1，HCCL/DDP；Python 3.11、torch/torch_npu 2.6.0、CANN 8.2.RC1、transformers 4.53.2。
- 保留上游 BF16 主体及 FP32 稳定性参数；每卡 batch=1、累积=1、global batch=4。
- 复用已有 OBS-backed LIBERO spatial 缓存，前 8 个示教各取第 16 帧和后续 10 个动作。归一化只覆盖这 8 个示教，未下载全量数据。
- 基线路径：首次真实更新、完整模型/优化器/RNG/样本进度保存，新进程严格恢复后再次更新；四卡动作输出 `[1,10,32]` 有限。未验证收敛或仿真成功率。
- 优化路径：完成全量有效梯度对照及 77 次真实更新/卡；没有另做优化路径完整 checkpoint 恢复验收。

## 兼容性修复中可复用的判断

1. 在设备探测前加载 torch_npu，显式选择设备和 HCCL。保留 CPU/CUDA 分支；safetensors 在当前版本经 CPU 加载后进入 NPU。
2. NPU 不支持 FP64 时间正弦嵌入时，在 CPU 保留原始计算，再按原调用方精度传回。此模型的 FP32 结果逐元素一致；不能将“改成 FP32”当作其他模型的等价修复。
3. 官方 JAX→PyTorch 转换检查缺失/多余权重键，只允许有源码依据的共享输出层及未参与动作损失的 expert LM head，不能用 strict=False 掩盖任意缺失。
4. 模型全部 requires_grad 不等于每个张量都参与 loss。本例有 805 个有效梯度张量，保留 unused-parameter 检测；不能因为加速愿望直接关闭。
5. 首步 warmup 学习率非常小，BF16 权重可能低于更新舍入间隔。观察实际参数变化及有效梯度，不能仅凭 optimizer.step 或部分 BF16 样本未变化判定训练成功/失败。

## 减少重计算后的梯度差异如何定位

原始逐层 checkpoint 外还有整段 Gemma checkpoint。只移除整段外层、保留逐层和视觉 checkpoint 后，首轮严格梯度检查未通过；原始路径自身重复也有误差。

固定权重、输入、各 rank RNG，无更新夹在比较之间：

| 控制条件 | 观察 |
|---|---|
| 普通 HCCL | 原始重复与候选都出现约 2.4414e-4 最大差，不能据此宣布候选等价 |
| `DDP.no_sync()` | 四卡各自本地全量梯度比较通过，最大差约 2.7940e-9 |
| 新进程 `HCCL_DETERMINISTIC=true` | 候选 vs 原始四卡通过，最大差 1.3970e-9、相对 L2 1.6750e-8 |

最终覆盖 805 个有效梯度张量、3,248,572,176 个元素，保持 atol=1e-7、rtol=1e-5。这将主要差异定位到 HCCL 归约非确定性，未发现去掉外层 checkpoint 造成额外显著误差；严格容差内一致不等于逐位相同。

进一步开启 torch 全局确定性时，图像插值分解请求了当前 NPU 不支持的内存布局。失败 attempt 保留退出码 1；后续仅将原非训练图像增强排除在模型确定性诊断开关之外。测速统一关闭 torch 全局确定性、保留确定性 HCCL。不能把诊断时变更的预处理语义混入速度结论。

## 性能结论与被保留为实验的方案

相同数据、精度和 batch，各 3 步 warmup + 8 步测量；每步取最慢 rank，再取中位数，所有慢样本保留。输入已预处理驻留 CPU；各块连续更新，不重置权重。

| 方案 | 秒/步 | 峰值 allocated GiB/卡 | 数值判定 |
|---|---:|---:|---|
| 原始 checkpoint + AdamW + 25 MiB | 1.3038 | 32.743 | 基线 |
| 减少外层 checkpoint + AdamW + 25 MiB | 1.1715 | 32.743 | 全量有效梯度通过；耗时 −10.15%，吞吐 +11.29% |
| 减少外层 checkpoint + fused AdamW + 25 MiB | 1.0725 | 30.393 | 参数/一阶动量严格检查失败 |
| 减少外层 checkpoint + AdamW + 50 / 100 MiB | 1.1553 / 1.1570 | 32.743 | 改桶后梯度严格检查失败 |

推荐减少重计算方案复测 1.1723 秒/步，基线复测 1.3026 秒/步。

- `NpuFusedAdamW` 在本环境拒绝 BF16；`torch.optim.AdamW(fused=True)` 原生 NPU 实现可运行混合 BF16/FP32。必须检查真实支持、fused 标志与 step tensor 设备，不能通过变更模型 dtype 来迎合优化器。
- 融合优化器对照抽取每个有效张量前 4096 元素，共 2,448,160 元素；从零动量开始，使用相同真实裁剪梯度在 peak LR 下更新三步。第三步参数最大差 9.1553e-5，参数/一阶动量未通过原阈值。它不是完整模型收敛或恢复测试。
- 确定性 HCCL 只保证相同配置的可复现性，不保证 25/50/100 MiB 桶的归约顺序相同。本例大桶额外收益仅约 1.38% / 1.24%，回到 25 MiB 又通过严格对照，保留 25 MiB。

当前推荐：`HCCL_DETERMINISTIC=true` + 仅移除整段 Gemma 外层 checkpoint + 保留逐层/视觉 checkpoint + 标准 AdamW + 25 MiB。实现只在项目实验进程中启用，原始 CLI 默认未改；不将 fused 的 17.74% 总收益冒充推荐方案收益。

## 下一次遇到同类问题

先复用同契约有效记录，再对未知差异做固定状态对照：原始重复 → 本地无通信梯度 → 确定性通信 → 候选。以实际证据选择步骤，避免将此顺序变成所有任务的固定门槛。优化器对照区分参数、两个动量和恢复语义；桶变化单独验证。不要放宽阈值掩盖未解释误差，也不要把数值小差异直接解释成任务效果退化。

Profiler 的累计 kernel 时间、同步阶段分解和无 profiler 的端到端耗时是不同量；不可直接相加或从带 profiler 的 Free 时间承诺可消除的空闲比例。以上短测不涵盖 DataLoader/视频解码、长程收敛、其他硬件拓扑或效果指标。
